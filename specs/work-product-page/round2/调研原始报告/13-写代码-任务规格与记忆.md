## 1. Taskmaster AI (eyaltoledano/claude-task-master)

- **Problem it targets:** Turning a PRD into a dependency-ordered task list that agents work through.
- **How it works:**
  - The PRD lives at `.taskmaster/docs/prd.txt`; the CLI and MCP parse it into tasks.
  - There are 36 MCP tools in total, a 15-tool "standard" set, and a 7-tool "core" set (`get_tasks`, `next_task`, `set_task_status`, `parse_prd`, `expand_task`, and others). Source: https://github.com/eyaltoledano/claude-task-master
  - Task fields: id, title, description, status, dependencies, priority, details, `testStrategy`, subtasks and optional metadata. Source: https://docs.task-master.dev/capabilities/task-structure
  - v0.41 added a `loop` command that runs Claude Code one task per iteration with "completion markers". v0.42 switched that loop's unattended execution to `--dangerously-skip-permissions` and added file locking and atomic writes for concurrent writers. Source: https://github.com/eyaltoledano/claude-task-master/releases
- **Cross-vendor:** MCP config is documented for Cursor, Windsurf, VS Code and Amazon Q CLI. Claude Code and Codex CLI can serve as model providers. State lives in the repo's `.taskmaster/` folder.
- **Human approval and acceptance:** There is no acceptance-criteria field; `testStrategy` is free text. "Done" is a `set_task_status` flip, and I found no documented verification step.
- **Status:**
  - Latest release is 0.43.1 (31 Mar; year inferred as 2026). The last commit on main is 23 Apr 2026 ("replace retired task-master.dev URLs"), and docs moved to tryhamster.com. https://github.com/eyaltoledano/claude-task-master/commits/main
  - About 28.2k stars.
  - License is MIT plus Commons Clause, which forbids hosted or competing products.
  - No commits for about 6 months, so it appears to be slowing down (inference).
- **Complaints (third-party):**
  - About 5k tokens of tool descriptions even at the core tier and about 21k at the full tier.
  - Sentry telemetry capturing prompts (issue #1681).
  - Agents ignoring prepared tasks.
  - Sources: https://chatforest.com/reviews/task-master-mcp-server/ and https://claudeissues.com/issue/43775-agent-ignored-prepared-task-master-tasks-wasted-usage-building-ad-hoc

## 2. Kiro (AWS)

- **How specs work:**
  - Each spec produces `requirements.md` (or `bugfix.md`), `design.md` and `tasks.md`.
  - Variants are Feature (Requirements-First or Design-First), Bugfix, and Quick Spec. Quick Spec runs "without approval gates".
  - "Run all tasks" builds a dependency graph and executes in waves. Source: https://kiro.dev/docs/specs/ (updated Oct 15, 2026)
  - Requirements use EARS ("WHEN … THE SYSTEM SHALL …"). Source: https://kiro.dev/docs/specs/feature-specs/ (Aug 4, 2026)
- **Correctness checks (property-based testing):**
  - Properties are extracted from EARS requirements, and generated inputs are shrunk on failure. Hovering shows the requirement→property→task link.
  - It is **IDE-only and optional by default**, and described as "evidence of correctness, not formal proof".
  - On failure the user chats to decide whether to change the implementation, the test or the **requirement**. Kiro can also auto-fix.
  - The docs do not say whether a task can be marked complete while properties fail. Source: https://kiro.dev/docs/specs/correctness/ (Aug 4, 2026)
- **Hooks:** Triggers include Prompt Submit, Agent Stop, Session Start/End, Pre/Post Tool Use, File Create/Save/Delete, and **Pre/Post Task Execution**. Only Pre Tool Use (and Prompt Submit in the IDE) are documented as able to block. Post Task Execution use cases are "running tests, linting". No veto on completion is documented. Sources: https://kiro.dev/docs/hooks/types/ and https://kiro.dev/docs/hooks/ (Oct 10, 2026)
- **Steering:** Files in `.kiro/steering/` (workspace) or `~/.kiro/steering/` (global). Kiro reads AGENTS.md, always included. Source: https://kiro.dev/docs/steering/ (Oct 6, 2026)
- **Kiro CLI:** Successor to the Q Developer CLI (migration guides exist). It has hooks, steering, MCP, ACP and headless CI mode. Source: https://kiro.dev/docs/cli/
- **Pricing:** https://kiro.dev/pricing/
  - Free: 50 credits.
  - Pro $20 / 1,000 credits; Pro+ $40 / 2,000; Pro Max $100 / 5,000; Power $200 / 10,000.
  - Overage $0.04 per credit.
  - Spec refinement, task execution and hook runs all consume credits.
- **Cross-vendor:** The spec files are plain markdown in the repo, so other agents can read them (inference). Execution, status tracking and property-based testing are Kiro-only.
- **Complaints:**
  - kirodotdev/Kiro#11786 (Oct 5, 2026): a runaway sub-agent was killed at 300 iterations, then "reported as succeeded and task marked [x]" while its last test run was failing. A maintainer called the defects "real and serious" (Oct 6). https://github.com/kirodotdev/Kiro/issues/11786
  - #11804: a design loop spent credits but never wrote `design.md`.
  - #10728: stuck in a task loop.
  - Böckeler (martinfowler.com, Oct 15, 2025) says a small bug became 4 user stories and 16 acceptance criteria, "like using a sledgehammer to crack a nut". https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html

## 3. Backlog.md (MrLesk/Backlog.md)

- **How it works:**
  - Tasks are markdown files in a repo `backlog/` folder, managed through a CLI, a TUI, a web board and MCP (`backlog mcp start`).
  - Setup is documented for Claude Code, Codex, Gemini CLI, Kiro and Cursor, so several vendors can read and write the same files.
  - Each task has acceptance-criteria checkboxes plus a project-wide Definition of Done checklist ("Tests pass", "Documentation updated") injected into every new task.
  - The README describes 3 human checkpoints: review the task and its acceptance criteria, approve the plan, then review the code and "Mark verified work Done". https://github.com/MrLesk/Backlog.md
- **Who closes tasks:** The agent guidelines tell the agent itself to `--check-ac` each item, check the DoD, write a final summary, then set `-s Done`, with "NEVER mark a task as Done without completing ALL items above". This is a prompt rule; I found no documentation that the CLI refuses Done with unchecked items. Agents may also add acceptance criteria themselves ("Update the AC first"). https://raw.githubusercontent.com/MrLesk/Backlog.md/main/src/guidelines/agent-guidelines.md
- **Status:**
  - v1.53.0 (24 Sep, presumably 2026).
  - v1.51 added an acceptance-criteria progress ring, a unified `isReady` flag, and dependency-cycle rejection.
  - About 7.0k stars, MIT license. https://github.com/MrLesk/Backlog.md/releases

## 4. Beads (steveyegge/beads, now gastownhall/beads)

- **Location:** steveyegge/beads now resolves to **gastownhall/beads**.
- **How it works:**
  - A "distributed graph issue tracker for AI agents, powered by Dolt."
  - Embedded Dolt in `.beads/` by default, or `bd init --server`. Sync runs via `bd dolt push/pull` to a git remote. `issues.jsonl` is only an export.
  - Hash IDs avoid merge collisions; `bd update --claim` claims atomically; `bd ready` lists open work with no blockers.
  - `bd setup` covers Codex CLI, Claude Code, Factory Droid, mux and Cursor, with an AGENTS.md snippet for other agents. https://github.com/gastownhall/beads
- **Acceptance and gates:**
  - Issues have `--acceptance`, `--design` and `--notes` fields.
  - `bd close` takes an optional `--reason` and **refuses unsatisfied gates without `--force`**.
  - Gate types are `human`, `timer`, `gh:run`, `gh:pr` and `bead`. A human gate "Requires manual bd close", and `bd gate check` does not evaluate human gates.
  - Source: https://raw.githubusercontent.com/gastownhall/beads/refs/heads/main/docs/CLI_REFERENCE.md
  - Inference: nothing authenticates that the closer is a human, and `--force` bypasses gates.
- **Status:**
  - v1.3.1 (2026-09-30) and v1.3.2-rc.2 (10 Oct). https://github.com/gastownhall/beads/releases
  - About 27.9k stars, MIT license.
  - Moved to Dolt-only storage in Feb 2026. That broke the simple solo SQLite-plus-git workflow; embedded "Beads Classic" mode was restored by Apr 2026. https://www.dolthub.com/blog/2026-04-02-restoring-beads-classic/
- **Complaints:**
  - Open data-integrity issues, e.g. #7289 (a retried create overwrites a concurrent writer's row, Oct 6, 2026), #7569 (backup restore fails) and #6956 (false "database corrupt" in worktrees). https://github.com/gastownhall/beads/issues
  - HN commenters: "only confuse[d] my agents", and it "will break under the weight of no-supervision". https://news.ycombinator.com/item?id=46624883
  - Yegge has described it as 100% vibe-coded, about 130k lines of Go (secondary source).

## 5. GitHub spec-kit

- **Workflow:** Now invoked as skills: `/speckit-constitution`, `-specify`, `-plan`, `-tasks`, `-implement` and **`-converge`**, plus bug and assessment workflows. https://github.com/github/spec-kit
- **Agents and status:**
  - Docs list 38 integrations (Copilot, Claude, Gemini, Codex, Kiro, Zed, Kilo Code, Forge and others) plus a generic fallback. https://github.github.io/spec-kit/ (Sep 28, 2026)
  - Latest release 1.2.0 (13 Oct); 1.1.x added an experimental MCP server and deprecated `taskstoissues`. https://github.com/github/spec-kit/releases
  - MIT license; about 141k stars as shown on the page.
- **Files:** Specs live in the repo at `specs/<NNN-name>/spec.md` and include testable functional requirements, measurable success criteria, and up to 3 `[NEEDS CLARIFICATION]` questions. https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md
- **`/analyze`:** "STRICTLY READ-ONLY". It treats the constitution as authoritative and maps FR/SC IDs to tasks. Remediation edits need user approval. https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md
- **`/checklist`:** "UNIT TESTS FOR REQUIREMENTS WRITING". It tests the quality of the requirements, not the implementation; the reviewer owns the boxes and the command never checks them. https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/checklist.md
- **`/implement`:** Stops and asks if checklists are unchecked, but the user can say proceed. It marks each task `[X]` with **no per-task test gate**; tests are validated only at the end. https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/implement.md
- **`/converge`** (PR #4609, June 2026):
  - Re-inspects the code against spec, plan and constitution, and states "completion claims are not evidence".
  - Its only write is appending a Convergence phase to `tasks.md`; it must not modify `spec.md` or `plan.md`.
  - It checks by code inspection, not by running tests. https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/converge.md
- **Complaints:**
  - #1865 (Mar 2026): "phantom completions". Two of about 770 `[X]` tasks had no code; the fix was a community verify-tasks extension, not core. https://github.com/github/spec-kit/issues/1865
  - #464: implement deviates from the plan.
  - #385: "Need for Human Oversight in Task Execution".
  - #620: spec drift.
  - Böckeler: "I'd rather review code than all these markdown files"; agents ignored research notes and duplicated classes.

## 6. Linear (agents, MCP, agent sessions)

- **Delegation:**
  - Agents are installed by admins and can be @mentioned or delegated issues. They are not billable seats.
  - They can "take most actions a human user can" depending on scopes, but cannot sign in, use admin functions or manage users. https://linear.app/docs/agents-in-linear
  - The directory lists 35 agents, including Codex, Cursor, GitHub Copilot, Factory, Devin, Sentry and Warp. https://linear.app/integrations/agents
  - The Codex integration launched Dec 4, 2025. https://linear.app/changelog/2025-12-04-openai-codex-agent
- **Agent sessions:**
  - Activity types are thought, elicitation, action, response and error.
  - Session states (pending, active, awaitingInput, complete, error, stale) are derived automatically from the last activity, so the session is **complete when the agent emits `response`**.
  - The plan checklist (preview) is replaced wholesale by the agent. https://linear.app/developers/agent-interaction
  - Best practice: move the issue to the first "started" status, set the agent as delegate, and for automation-delegated work "leave assignment up to a human". https://linear.app/developers/agent-best-practices
- **MCP:** `https://mcp.linear.app/mcp`, read-write by default with a `/readonly` variant. Clients include Claude, Codex, Cursor, VS Code, Windsurf, Zed and Jules. https://linear.app/docs/mcp
- **Assessment:** State is in Linear's cloud and is genuinely cross-vendor. No acceptance-criteria object or evidence-gated closure is documented.

## 8. Claude Code memory and AGENTS.md

- **CLAUDE.md:** Covers project, user and org scopes, with `@imports` up to 4 hops. The docs say memory is "context, not enforced configuration" and point to PreToolUse hooks for blocking.
- **AGENTS.md:** Claude Code now **reads AGENTS.md natively** (v2.1.277+) when no CLAUDE.md is present.
- **Auto memory:** `~/.claude/projects/<project>/memory/MEMORY.md`, loading the first 200 lines or 25KB. It is **machine-local** and not shared across machines. https://code.claude.com/docs/en/memory
- **Tasks:** Stored in `~/.claude/tasks/`. They are shareable across *Claude* sessions with `CLAUDE_CODE_TASK_LIST_ID`, so single-vendor. https://code.claude.com/docs/en/interactive-mode
- **AGENTS.md standard:**
  - Stewarded by the Agentic AI Foundation under the Linux Foundation.
  - Listed readers: Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Copilot coding agent, Windsurf, Augment and others. https://agents.md/
  - AAIF also hosts MCP, goose, A2A and agentgateway; platinum members include AWS, Anthropic, Google, Microsoft and OpenAI. https://aaif.io/about/
  - It carries instructions, not task state.

## 12. Handoff tools

- **Amp handoff:** Starts a new thread with "the relevant context"; since Jan 13, 2026 you can trigger it by asking the agent. It works within Amp only. https://ampcode.com/news/ask-to-handoff and https://ampcode.com/docs/threads
- **Cline `/newtask`:** Handoff to a fresh Cline task (see section 7).
- **Continuous-Claude-v3 (parcadei):**
  - Ledgers in `thoughts/ledgers/CONTINUITY_*.md` and YAML handoffs in `thoughts/shared/handoffs/<session>/`.
  - A PreCompact hook auto-saves and SessionStart reloads; Postgres plus pgvector stores memory.
  - It is built on Claude Code hooks, so Claude-only. MIT license, about 3.9k stars. https://github.com/parcadei/Continuous-Claude-v3
- **Agent Client Protocol (Zed):** A JSON-RPC protocol between editors and agents (Claude Code, Codex, Gemini CLI and others run in Zed and JetBrains). It is not a task or state handoff format; the site shows no session-transfer feature. https://agentclientprotocol.com/

## 13. Other shared-state tools

- **MCP Agent Mail (Dicklesworthstone):**
  - Agent identities, inboxes and threads, plus advisory file reservations with an optional pre-commit guard.
  - Messages are stored as markdown in a per-project git repo with a SQLite index.
  - Supports Claude Code, Codex, Gemini CLI and Droid. A "HumanOverseer" can send messages agents must prioritise.
  - Beads owns task status; Agent Mail carries conversation, with shared `bd-123` IDs.
  - The Python version is unmaintained; the Rust successor is at v0.3.39. https://github.com/Dicklesworthstone/mcp_agent_mail and https://github.com/Dicklesworthstone/mcp_agent_mail_rust
- **Task Orchestrator (jpicklyk):**
  - SQLite-backed, works with any MCP client. "Prompt-based frameworks hope the LLM follows instructions. This one blocks the call if it doesn't."
  - Items move only via `advance_item`. Schemas require named notes per phase, e.g. a `requirements` note before leaving the queue, and missing notes produce an error. The check appears to be presence, not content.
  - Actor authentication is optional (via a Claude Code hook); there is no permission model for who may advance.
  - MIT license, about 208 stars. https://github.com/jpicklyk/task-orchestrator
- **Shrimp Task Manager:** `verifyTask` marks a task completed only if `score >= 80`, but **the score is a tool argument supplied by the calling agent**, so it is a self-graded gate. MCP, MIT license, about 2.1k stars. https://raw.githubusercontent.com/cjo4m06/mcp-shrimp-task-manager/main/src/tools/task/verifyTask.ts
- **Vibe Kanban:**
  - Kanban that runs 10+ agents (Claude Code, Codex, Gemini, Copilot, Amp, Cursor and others) in worktrees with diff review. Apache-2.0.
  - **Sunsetting**, announced Apr 10, 2026: remote services closed after 30 days and it became community-maintained and local-only. https://www.vibekanban.com/blog/shutdown

## Synthesis

### Shared cross-vendor task or goal state (verified)
- **Through repo files plus CLI or MCP:** Backlog.md, Beads, spec-kit and Taskmaster are each documented with multiple vendors. Kiro specs are readable by others but executed only by Kiro (inference).
- **Through a cloud or server:** Linear (the strongest real multi-vendor assignee model, with Codex, Cursor, Copilot, Devin and others as delegates), Task Orchestrator, Shrimp and Agent Mail.
- **Memory, not tasks:** mem0, Basic Memory and Pieces share across vendors.
- **Single-vendor:** Claude Code auto memory and Tasks, Amp handoff, Cline `/newtask`, Continuous-Claude.
- **Instructions only:** AGENTS.md is cross-vendor but carries no state.

### First-class acceptance criteria
- **Yes:** Kiro (EARS), spec-kit (FR/SC plus acceptance scenarios), Backlog.md (AC checkboxes plus DoD), Beads (`--acceptance`).
- **Partly:** Taskmaster has only a free-text `testStrategy`.
- **No acceptance object documented:** Linear, the memory tools, Task Orchestrator (required notes instead) and Shrimp.

### Enforcing acceptance at closure
- **None verified.** No product I found refuses "done" based on evidence that the acceptance criteria are met, checked by something other than the implementing agent.
- **Structural gates only:**
  - Task Orchestrator blocks on missing notes (presence).
  - Beads `bd close` refuses unsatisfied gates and dependencies, including human and `gh:pr` gates, but `--force` bypasses them.
  - Shrimp has a threshold, but the agent grades itself.
  - spec-kit `/implement` pauses on unchecked requirement checklists, but the user can override.
- **After the fact:**
  - spec-kit `/converge` ignores checkboxes ("completion claims are not evidence") and appends missing work, but it does not unmark tasks or run tests.
  - Kiro property-based tests are optional and IDE-only, and Post Task hooks have no documented veto.
- **Honor system (the agent ticks the box):** Backlog.md, Taskmaster, Linear (`response` closes the session), Claude Code Tasks, Kiro `tasks.md`, spec-kit `[X]`.
- **Documented failures:** Kiro #11786 ([x] with failing tests) and spec-kit #1865 (phantom completions).

### "Agent proposes, human decides" for requirement changes
- **Closest:** spec-kit's read-only `/analyze` (remediation needs approval), `/converge` (forbidden from editing spec and plan) and reviewer-owned checklists. Kiro's phase approval gates for Feature Specs (skipped in Quick Spec) and its "decide whether to change implementation, test, or requirement" step on property-test failure. Beads human gates.
- **All prompt- or convention-enforced:** none prevents an agent with file or MCP write access from editing requirements (inference from docs; no locking or permission feature found).
- **Agents explicitly allowed to change scope:** Backlog.md ("Update the AC first"). Linear agents have human-equivalent edit scopes.

### White space (inference)
No product combines all four of:
1. Cross-vendor shared task state.
2. Structured acceptance criteria.
3. Closure that requires evidence checked independently of the implementer.
4. Requirement edits restricted to proposals that a human accepts.

Each existing tool has at most two of these.
