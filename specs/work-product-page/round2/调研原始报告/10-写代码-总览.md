## 0. What Molis Work actually ships (verified; this sets what we can claim)

- **The repo is real and active, but very small.** It is MIT licensed, has 5 stars, was created 2026-08-15, and was last pushed 2026-10-16. Source: `gh api repos/molis-ai/molis-work`.
  - Its description is "Goal truth source shared by people and Agent Runtimes".
  - The product was **renamed from GoalBoard on 2026-09-15**. The v0.2.0 tag and its CLI/MCP names are still `goalboard*`. Source: docs/releases/CHANGELOG.md in the repo.
- **v0.2.0 (2026-09-11) is a source-only release.** Its notes say the public macOS installer comes only after Developer ID signing and notarization ([release](https://github.com/molis-ai/molis-work/releases/tag/v0.2.0)).
  - The last DMGs are **v0.1.13**: an unsigned pre-release, named GoalBoard, dated 2026-08-31.
  - The README still says "Public macOS installers remain pending Developer ID signing and Apple notarization" ([README](https://github.com/molis-ai/molis-work)).
- **Runtimes.** Built-in recipes cover Codex, Claude Code, OpenCode, Pi Agent and Grok Build. Others connect through MCP plus the shared Skill. The README states "Molis Work does not dispatch work for you."
- **Authority model.** Sources: docs/runtime.en.md and docs/mcp.en.md.
  - Agents **can** do these directly: create goals, set an initial outcome, **add** requirements, write notes and reports, and record concerns.
  - Agents **need a human decision tied to the exact change** to replace an outcome, revise or retire or weaken a requirement, or remove human acceptance.
  - Changes to the goal tree and dependencies are proposals. The user approves them in a protected UI.
  - A runtime has no `event_decide` or `goal_tree_decide` authority. It cannot fill in an identity or a `user_confirmed` field to approve its own change.
  - **So "agents can only propose structural or agreement changes" overstates it.** Adding requirements needs no approval.
- **Closure.** `goals.closure.submit` only takes effect with `completion_applied=true`.
  - If versions are current but gaps remain, the closure is saved as `recorded=true, completion_applied=false` with reasons. Stale or invalid versions are rejected outright.
  - The gates are: support for every current requirement, a still-valid human conclusion where `human_decision_required=true`, finished dependencies, and no open blocking concerns.
  - **Crucially, the protocol itself says reports "neither create user approval nor independent verification".** A requirement that doesn't need a human "can use a supporting Runtime report" (skills/goal-advance/references/protocol.md). The support is still the agent's own assertion. Molis does not run tests.
- **Handoff.** PRODUCT.md says cross-runtime work happens only through a user-confirmed Handoff. It passes the current Goal plus necessary context to the target runtime and creates a **new** session there. It does not move the transcript. I did not confirm that this is in the v0.2.0 build. The v0.1.11 pre-release was titled "Human Handoffs".
- **Main, after v0.2.0: breaking changes and no upgrade path.** Each database accepts only its current schema version. v0.2.0 Homes cannot be opened by new builds, and no upgrade tool ships (CHANGELOG [Unreleased]). The next version will be 0.3.0.
- **Small print.** Runtimes must start a new session to load tools. v0.2.0 cut the runtime tools from 57 to 35. Desktop is macOS only; the web service can run in the foreground elsewhere.

## 1. The closest competitor, which the brief missed: Traycer Desktop (verified)

- **What it is.** "Open-source desktop app for running Claude Code, Codex, Cursor and other AI coding agents in parallel, with shared plans and code review" ([docs](https://docs.traycer.ai/index.md)).
  - MIT, 1,612 stars, Desktop v1.5.1 released 2026-10-10 ([GitHub](https://github.com/traycerai/traycer)).
  - Runs on macOS, Windows and Linux. The IDE extension is being retired on 2026-10-31 ([notice](https://docs.traycer.ai/extension/index.md)).
- **Shared state across vendors.** A Task holds agents, files, terminals and **artifacts** (specs, tickets, stories, reviews) that "outlast any single conversation".
  - Supported agents include Claude Code, Codex, OpenCode, Cursor, Droid, Copilot, Amp, Antigravity and Grok ([agents](https://docs.traycer.ai/agents-and-models/coding-agents.md)).
  - Agent-to-agent messaging works across Tasks, and agents can read each other's transcripts.
  - First run imports existing Claude Code, Codex and OpenCode sessions ([first run](https://docs.traycer.ai/first-run.md)).
- **Plan and "done".**
  - `traycer-ticket-breakdown` "iterates until you approve the set".
  - `traycer-execute` reviews each batch against the plan. "Tickets that pass are marked done", and product drift stops the run and comes back to you.
  - `traycer-autobuild` has you approve a spec, a grading rubric and a verification method. A separate evaluator agent then grades each sprint.
  - **These are skills, not enforced gates.** Traycer "doesn't fail a turn when a skill is skipped" ([artifact workflow](https://docs.traycer.ai/concepts/artifact-workflow.md)). "Done" is decided by a reviewer agent; no human acceptance is enforced.
- **Rate limits.** It can automatically route a blocked chat to another account or an equivalent model. This is off by default and covers chat agents only ([routing](https://docs.traycer.ai/settings/model-routing.md)).
- **State and account.**
  - Sign-in with a Traycer account is required ([first run](https://docs.traycer.ai/first-run.md)).
  - Tasks are held on the host and **synced to the cloud** ([sync](https://docs.traycer.ai/concepts/sync-and-offline.md)).
  - Free for individuals; Sync costs $20 per user per month for teams ([pricing](https://docs.traycer.ai/account/pricing.md)).
  - It has a mobile app, notifications and remote hosts.
- **Verdict.** Traycer is ahead on parallel runs, vendor coverage, platforms, rate-limit routing and mobile. Molis is different on:
  - local-only with no account;
  - a governed record where agents cannot weaken requirements or self-approve;
  - closure gated on human acceptance at the protocol level, not in a prompt.

## 2. The name collision: Claude Code and Codex both ship "goals" (verified)

- **Claude Code `/goal`** ([docs](https://code.claude.com/docs/en/goal.md); requires v2.1.139 or later).
  - It is a session-scoped completion condition and wraps a prompt-based Stop hook.
  - After each turn, a small fast model judges "met / not yet / impossible" so that completion is "decided by a fresh model rather than the one doing the work".
  - The evaluator "doesn't run commands or read files independently". It reads only the transcript.
  - One goal per session. It survives resume. It pauses on usage limits and resumes when they reset.
- **Codex Goals** ([cookbook](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex.md)). Requires Codex 0.128.0. It became non-experimental in Codex app 26.519 on 2026-05-21 ([changelog](https://learn.chatgpt.com/docs/changelog)).
  - It is a thread-scoped "completion contract". It "should be complete only after the objective is checked against" tests, logs and artifacts.
  - It supports pause, resume and clear, plus a budget.
  - Mobile can resume blocked or usage-limited runs (iOS update, 2026-07-20).
- **Implication.**
  - Developers will hear "Goal" and assume it is `/goal`. The page has to say up front that a Molis Goal is a **persistent, multi-session, multi-vendor record**: requirements, dependencies, concerns, human acceptance and decisions.
  - A vendor `/goal` is a **single-session keep-going loop** with model-judged completion.
  - On **automatically running checks**, the vendor loops are ahead: the agent runs the tests inside the loop. On durability, scope and human authority, Molis is ahead.

**Bottom line on shared cross-vendor state.**
- Repo-file systems (spec-kit, OpenSpec, Beads, Backlog.md, BMAD) are *already* vendor-neutral and git-shareable. **That is the main reason "shared across vendors" alone is not a differentiator.**

## 4. How developers work with agents today: five patterns

For each: the unsolved problem, who addresses it, and where Molis stands.

1. **Single interactive session (terminal/IDE pairing)**
   - Problem: new-session amnesia; upkeep of CLAUDE.md, AGENTS.md and progress files.
   - [PK] Anthropic's "Effective harnesses for long-running agents" (Nov 2025) recommends a progress file plus a JSON feature list with a "passes" flag. Its stated reason: agents mark features done prematurely ([PK URL](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
   - Addressed by: repo memory files, Claude Tasks, Codex threads, Amp handoff.
   - **Molis: partly overlapping.** Its edge is that state is structured (requirements, gaps, next step) and survives across vendors. Repo files already survive across vendors, but they are ungoverned.
2. **Plan/spec-first**
   - Problem: specs drift; agents rewrite scope; checklists are honor-system.
   - Mass adoption is verified by stars: spec-kit 141k, OpenSpec 72k, BMAD 54k.
   - Addressed by spec-kit, OpenSpec and Kiro. Their gates are prompts or git review (OpenSpec archive explicitly does not block).
   - **Molis: genuinely different** on enforcement. Weakening a requirement needs a decision tied to that change, and agents can't self-approve.
   - **Behind** on authoring ergonomics and on repo-native, PR-reviewable specs.
3. **Parallel local agents in worktrees**
   - Problem: review bottleneck; losing track of what each agent is doing.
   - [PK] Simon Willison, "parallel coding agent lifestyle", Oct 2025.
   - Addressed well by Superset, Conductor, Emdash, Claude Squad, Traycer and Cursor.
   - **Molis: behind, and should not compete here.** It does not dispatch. Goal-bound terminals and the menu-bar capsule are status aids, not orchestration.
4. **Async cloud agents producing PRs from issues** (Copilot coding agent, Agent HQ, Codex cloud, Jules, Devin, Cursor cloud)
   - Problem: the PR becomes the only record; done means merged; acceptance criteria live in the issue text.
   - **Molis: gap.** A local MCP on your Mac cannot be reached by cloud agents.
5. **Long-running autonomous loops** (Ralph [PK](https://ghuntley.com/ralph/), Claude `/goal`, Codex Goals; V)
   - Problem: premature or false "done". [PK] METR's reward-hacking post (June 2025) and the Stack Overflow 2025 survey (most developers don't trust AI accuracy; "almost right" is the top frustration) are context here.
   - Vendors now judge completion with an evaluator model (Claude) or a self-audit against evidence (Codex), but **within one session and one vendor, judged from the transcript.**
   - **Molis: complementary, not ahead.** It adds human acceptance and cross-session gates but does not itself verify. Worth integrating with these loops (see section 6).
6. **Cross-cutting: several vendors at once and rate-limit switching.**
   - Traycer (routing to another account or model), Codex (mobile resumes usage-limited runs) and Claude `/goal` (resumes when the limit resets) cover this.
   - **Molis handoff:** user-confirmed, creates a new session in the target runtime. It overlaps; Traycer automates more.

## 5. Claims

### Defensible (phrase exactly like this)

- "One Goal record that Claude Code, Codex, OpenCode, Pi Agent and Grok Build read and write through the same MCP actions. Other tools connect over MCP."
- "Kept locally in a per-project SQLite database under ~/.molis-work. No Molis account and no cloud sync."
  - The contrast is citable: Traycer requires sign-in and syncs Tasks to the cloud.
- "A Goal outlives any session. Outcome, requirements, dependencies, concerns, decisions and history carry across sessions and across vendors."
  - The contrast is citable: Claude `/goal` is per session; Codex Goals are per thread.
- "Agents can record work and propose changes. They can't quietly replace an agreed outcome, weaken or retire a requirement, approve a structure change, or sign off a human-acceptance requirement. Those decisions are written only by you, in the local UI."
- "'Done' is an explicit close-out. It does not take effect while a requirement has no recorded support, a human-acceptance requirement lacks your sign-off, a dependency is unfinished, or a blocking concern is open."
- "Terminals open bound to a Goal. The macOS menu bar shows the current Goal and its next step."

### Must NOT claim

- "Verifies / proves the work is done", "evidence-checked" (if it implies checking the evidence itself), or "tests pass". Support is agent-reported; the protocol says reports are not independent verification.
  - Say instead: "**checks that each requirement has recorded support** and **your** sign-off where required."
- "Agents can only propose changes." They can create goals and add requirements directly.
- "The only way to share work across Claude Code and Codex." Traycer, Superset, Emdash, Claude Squad, Agent HQ and every repo-file system already do this.
- "Orchestrates / runs agents in parallel / assigns work." The README says it does not dispatch.
- Presenting "Goal" as new without contrasting it with `/goal`.
- "Download v0.2.0." It is source-only. The signed public installer is pending. The last DMG is an unsigned v0.1.13 named GoalBoard.
- "Seamless handoff of the conversation." Handoff starts a new session with the goal and context.
- Any main-branch feature as released: context bar, assistant, ⌘K, plugin builder, 12-step workflows.
- Windows or Linux desktop support.
- Any traction or "trusted by developers" language (5 stars).
- "Upgrade safely." Main refuses v0.2.0 databases and ships no upgrade tool.

## 6. Gaps and ideas for the team

1. **Machine-verified support.**
   - Let a requirement bind to a check (a command, CI status, or a PR merged with checks green) that Molis runs or reads itself.
   - Label every support item as *agent-asserted*, *machine-verified* or *human-accepted*.
   - This would move Molis from bookkeeping to a real differentiator over `/goal`'s transcript-only evaluator.
2. **Become the layer above vendor goal loops.**
   - Generate a Claude `/goal` condition or Codex Goal from a Molis Goal's open requirements.
   - Ingest the loop's verdict and transcript excerpt as a report.
3. **Interoperate with repo files.**
   - Import and export spec-kit, OpenSpec, Backlog.md and Beads.
   - Link commits and PRs as support.
   - Developers already keep specs in git; competing with that is a losing battle.
4. **Plug into the orchestrators.**
   - Ship MCP setup snippets for Superset, Conductor and Traycer.
   - Show which worktree or session is serving which Goal.
5. **One-click handoff when one vendor hits a rate limit** (e.g. Claude → Codex). Benchmark it against Traycer's routing.
6. **Cloud-agent reach.** Copilot, Codex cloud and Jules can't reach a local MCP. Consider a remote MCP bridge or a GitHub-issue sync.
7. **Trust basics before courting developers.**
   - A signed and notarized build.
   - A real migration path. A "truth source" that refuses its own old databases undermines the pitch.
   - Measure the token cost of the 35-plus runtime MCP tools.
8. **"Needs you" notifications** (menu-bar badge and macOS notifications) for pending decisions. Traycer and the vendors' mobile apps already set this expectation.
