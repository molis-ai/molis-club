## 1. Plugin SDK, manifest, third-party install

**Manifest:** `PluginManifest` is in `packages/contracts/src/platform/plugin.ts:180-249`.
- **Identity and basics:** `schema_version 1|2`, `plugin_id`, `version`, `kind` (`"native"|"integration"|"app"`, L114).
- **Publisher:** `publisher.{publisher_id, signature}`. A changed signature counts as a new plugin.
- **Entrypoints and permissions:** `entrypoints`, `permissions`.
- **Capabilities:** `capabilities.{provides, consumes}`. Putting host action ids in `consumes` lets the plugin call them through `services.actions.invoke` (PLUGIN-PLATFORM.md:23).
- **Artifacts:** `artifacts.produces[]` (with optional preview/pin/compare/continue actions) and `artifacts.consumes[]`. There are also `process_items.{produces,consumes}`.
- **UI:** `ui.{contributions, embedded_plugins, views, commands}`. Each view has a slot from `UI_VIEW_SLOTS = ["navigator","stage","settings","island","side"]` (`packages/contracts/src/platform/ui.ts:23`).
- **v2 fields:**
  - `ports` (`{inputs, outputs, input_groups}`, `plugin-wiring.ts:77`)
  - `events`, `routes` (mounted under `/api/plugins/<id>/`), `requires`
  - `agent` (`AgentManifest`: roles, prompts, skills, subagents)
  - `methods`: skills offered to *other* agents. Their `tools` are limited to `METHOD_TOOLS` (`plugin-agent.ts:29`).
  - `upgrade_compatibility`, `actions` (registered in the shared action catalog), `action_scenes`.

**Can a third party install an external plugin today? No.**
- `docs/system/THIRD-PARTY-PLUGINS.md:3` is a plan only, dated 2026-10-08: "本步只写计划，不实现" ("this step only writes the plan").
- Its "没有" (what is missing) list, L22-29: no `install` command, no trust root, no loader that starts a plugin from a verified package, and the sandbox only accepts generated-plugin shapes.
- `PLUGIN-DEVELOPMENT.md` (packaging section, ~L316) says the same: "用户把这样的包装进自己的 Home 目前没有路径" ("there is currently no way for a user to put such a package into their Home").

**What does exist (`tooling/plugin-cli/src/cli.ts:24`):** the commands `validate`, `create`, `pack`, `identity`, `sign`, `verify` and `dev`.
- `dev` requires `--allow-unsigned-development` (L32). It loads source in-process into an isolated state directory; grants there are explicitly "不是 OS sandbox" (not an OS sandbox).
- Signing is Ed25519. Publisher identity is `ed25519:sha256:<spki hash>` (`packages/plugin-runtime/src/package-verification.ts`).

**Planned design (not implemented):**
- Commands: `molis-work plugin install <bundle.json>`, `list`, `upgrade`, `disable`, `enable`, `uninstall`, `trust list|revoke` (L41-45).
- Trust: the user confirms and pins a publisher key on first install.
- Execution: always `execution:"sandbox"`, macOS only, and the UI is drawn by the platform.
- Workbench entry: a "从文件安装" (install from file) button.
- Slices P-1 to P-5 are not on the roadmap yet.

**Plugin market (插件市场):** built-ins only. `pluginMarketCards()` maps over `BUILTIN_PLUGIN_CATALOG` (`apps/workbench/src/plugin-catalog.ts:218-236`). Developer mode only reveals entries marked `developer:true`; today that is just Text Stats (`builtin-plugins.ts:418`). It is switched on by the env var `MOLIS_WORK_DEVELOPER_MODE=1` (PRODUCT.md:31). A store with listing and review (BL-058) is deferred.

**Timing:**

## 2. "Let AI build a plugin" (插件创作工作台)

**Sources:** `plugins/native/plugin-builder/README.md` and `specs/archive/plugin-builder/work-items/agent-built-plugins/spec.md` §2 (L46-56).

**Steps:**
1. The user describes the plugin in one sentence, optionally with text or a CSV.
2. The main design agent asks at most one round of clarifying questions.
3. It proposes 2–3 plans. Each lists the platform capabilities, other plugins' actions and network domains it needs.
4. The user picks one. The host freezes a "功能合同" (function contract: operations, input/output schema, errors), a manifest draft and a project skeleton.
5. Two tracks run in parallel:
   - UI: Jev (the agent that picks components) chooses parts from the spec board, which is the platform UI catalog `/__ui/catalog`.
   - Backend: a new Prologue code agent writes operations and tests.
6. The host runs gates G1–G7 per operation (spec L118-131): manifest, strict typecheck against the SDK, bundle with Node fs/net/process modules forbidden, contract conformance, tests in a mock host, a sandbox trial with preview data, and browser-driven acceptance. A component is marked "已接通" (connected) only after its operation passes.
7. Install: one grant sheet covering its own data, what it reads and what it changes. Irreversible actions are not exposed.
8. The plugin is installed as `io.molis.work.generated.<id>` (`agent-workflow.ts:221`). Each function becomes a catalog action, `generated.<build8>.<fn>`, for the user, agent, workflow, MCP and plugin audiences (PLUGIN-DEVELOPMENT.md ~L30-50).
9. Editing again creates a new draft. Upgrade and rollback are supported, and new permissions need fresh consent.

**Needs a model?** Yes. README:5 says "先配置模型并关联工作区" (first configure a model and link a workspace), and D11 says it uses the user's configured model.

**UI ownership:** the platform renders it from the spec board. README:3 says "插件没有自己的前端代码" (the plugin has no frontend code of its own). `apps/local-host/src/plugin-builder/installed.ts:1-4` confirms the plugin's code never runs in the host or the page.

**Limits:**
- macOS only: `packages/plugin-sandbox/src/runner.ts:42` throws `sandbox.unsupported_platform`.
- No custom frontend components and no marketplace or cross-user distribution (spec L240).
- Network goes only through the host proxy with a domain allowlist.
- Generated plugins do not register `methods`.

**Maturity:** status `partial` (README:10 and SSOT-MATRIX). The studio-v3 spec says "方案已定…待执行" (plan settled, awaiting execution). The recorded first-pass design acceptance rate is 42/80 (README:30).

**Timing:** after v0.2.0. The package dates from 2026-09-23 (`735c3539`) and the agent-built sandbox studio from 2026-09-26 (`eff5b09d`).

## 3. Cross-plugin workflows and Functions

**Workflows** (`plugins/native/workflows`): a chain of up to 12 stations (`parseChain`, `src/model.ts`). Each instance keeps its own snapshot of the chain, its progress and every handoff.

**Station types:**
- A content site: a `WorkflowContentBinding` with list/read/receive/create action references.
- An action step: any registered action, with fields filled from title/body/source/url/date or fixed values.

**Handoffs:** the README names three, but `model.ts:11` actually has four, `"function" | "ai" | "manual" | "judgment"`:
- `function` is template conversion: `title_template`/`body_template` with placeholders 标题/正文/来源/链接/日期 (`WORKFLOW_TEMPLATE_FIELDS`). It is ready only once a body template exists (`linkReadiness`).
- `ai` needs instructions plus a configured text model.
- `manual` means a person decides what to hand over.
- `judgment` checks the step with a published Choice rule from Functions and lets through only the chosen results.
- The README says `kind:"function"` is kept only as the stored value for template conversion.

**What Functions is:** `modules/functions` holds judgment functions, not template rules. That means drafts, immutable published Choice/Score/Noul rules (run through TypeSafe), samples and judgment records. Its editor is in `apps/workbench/src/functions`, under 能力 (Capabilities); there is no Functions plugin. Running a rule from an external client requires a grant on `functions.invoke`.

**Plugins that declare `defineWorkflowContentActions`:**
- Feed, Inbox and Jelly can receive.
- Pages, Forms, Dataset, PPT and 灵光 can receive and also create blanks (`create:true`).
- 成果/Artifacts is a source only (`receive:false`).

**Ports are a separate mechanism.** It is the v2 "输入图" (input graph) in PLUGIN-PLATFORM.md §4, implemented by `PluginInputGraph` in `packages/plugin-runtime/src/wiring.ts` with a `plugin_port_bindings` table. Bindings have an origin of `user`, `default` or `unique`, and carry typed artifact versions.
- Plugins declaring ports: Coding, Diff, Files, Git, Shelf and Text Stats.
- Example: Diff's before/after inputs default to the Files ports (`plugins/native/diff/src/manifest.ts:66-80`).

**Timing:** after v0.2.0. Functions dates from 2026-09-20 (`261c410d`, via `--follow`), workflows from 2026-09-26 (`ad21cff2`) and `workflow-content.ts` from 09-27.

## 4. Action catalog (能力注册一次，到处可用)

- **The principle:** PRODUCT.md:34. Plugins declare `actions` once.
- **Who can call:** each action has `audiences` from `"user"|"agent"|"workflow"|"mcp"|"plugin"` (`packages/contracts/src/platform/actions.ts:31`). Reversible agent actions are automatically open to plugins (`actionReachesAudience`, L263).
- **Pages:** call through the same host actions.
- **The Assistant and characters:** use the capability-gateway tools find, read and change-capability plus suggest-action (`METHOD_TOOLS`). Changes need the user's confirmation.
- **Workflows:** discover stations and steps from the catalog.
- **External MCP:** a single `molis-work-mcp` process exposes each action as the tool `molis_work_v1_action_<id>__v<ver>` (`apps/mcp/src/action-tools.ts:16-18`).
- **Grants:** set per client, per project or home scope, and per action by `createMcpActionGrant` (`apps/local-host/src/mcp-action-grants.ts`).
- **Where grants live in the UI:** the 能力 (Capabilities) settings page has four sections: 能力库, 服务连接, 对外接入 and 调用记录 (`apps/workbench/src/capabilities.ts:30-32`). 对外接入 (external access) is also listed in `settings-sections.ts:36` under the group "工具与接入".
- **Timing:** after v0.2.0, 2026-09-26/27 (`9e0182f1`, `27d750ee`).

## 5. Market and switcher, add/remove, updates

**Add and remove:** a project can add or remove plugins in place from the switcher grid. Not added shows a "+", added shows a red trash can, and there is a Dock pin (DESIGN.md:309).
- Implemented per `specs/archive/plugin-picker-dock` (archived 2026-10-02 as implemented, PR #171).
- Removal from the market came in `specs/archive/plugin-market-remove` (2026-10-01), through `POST /api/settings/projects/:id/plugins` and its removal route.
- Goals cannot be removed. Personal plugins can only be hidden; per-project disabling is BL-088.

**The update dot:** `plugin-workbench.ts:21-37` polls `/api/plugins/runtime/updates` (`apps/local-host/src/coding-surface.ts:181`). That returns `supervisor.upgradeCandidates()` (`packages/plugin-runtime/src/supervisor.ts:338-360`):
- It skips bundled built-ins: "it follows the Host's build at start: the market has nothing to confirm for it".
- It lists only runtime entries whose target version is higher than the installed one, with a compatible or migratable mode.

There is no external source behind this, so it is not an external-plugin update channel.

**Timing:** after v0.2.0. v0.2.0 had only 4 native plugins (artifacts, feed, goals, work); `plugin-catalog.ts` appears from 2026-09-27.
